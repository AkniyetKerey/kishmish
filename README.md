# Kish-Mish — сайт-меню с онлайн-заказом

Одностраничный сайт-меню для сети точек питания с оформлением заказа через
WhatsApp, полноценным бэкендом на Supabase и отдельной админкой для
управления меню.

**Живой пример потока:** клиент выбирает филиал → смотрит меню → собирает
корзину → жмёт "Заказать" → уходит в WhatsApp с готовым текстом заказа,
адресом и суммой → заказ также сохраняется в базе.

## Как это работает — коротко

Оба "конца" проекта — сайт для клиентов (`index.html`) и админка
(`admin.html`) — обращаются к данным **только** через `js/api.js`. Ни
`menu.js`, ни `admin.js` не знают, откуда именно приходит меню — из
Supabase или из локальной заглушки. Переключается одним флагом:

```js
// js/api.js
const USE_SUPABASE = true; // false — работать локально без базы (для разработки)
```

```
Клиент (index.html) ──┐
                       ├──> api.js ──> Supabase (одна общая БД)
Админка (admin.html) ──┘
```

### Путь заказа
1. Клиент выбирает филиал (экран выбора при первом визите)
2. `api.getMenu()` тянет меню именно для этого филиала
3. Корзина и состояние (тема, адрес, тип заказа) сохраняются в `localStorage`
   между визитами
4. При оформлении: заказ пишется в таблицу `orders` через `api.placeOrder()`,
   параллельно открывается WhatsApp с готовым текстом — на номер **именно
   этой точки** (см. `BRANCH_PHONES` в `config.js`)

### Путь редактирования меню
1. Заходишь в `admin.html`, входишь через Supabase Auth (только ты знаешь
   пароль — обычные посетители сайта войти не могут)
2. Добавляешь/редактируешь/удаляешь категории и товары, переключаясь между
   вкладками филиалов
3. `api.saveMenu()` вызывает SQL-функцию `replace_branch_menu` — она
   переписывает меню филиала **одной транзакцией**: либо сохранится всё
   целиком, либо (при сбое) не сохранится ничего — промежуточных "наполовину
   битых" состояний быть не может

## Настройка Supabase (с нуля)

1. Зарегистрируйся на [supabase.com](https://supabase.com), создай новый
   проект
2. **SQL Editor → New query** — примени файлы из `supabase/` **строго по
   порядку**:
   1. `schema.sql` — создаёт таблицы
   2. `functions.sql` — атомарная функция сохранения меню
   3. `rls_secure.sql` — ограничивает запись меню только авторизованным
   4. `rls_orders_hardening.sql` — защита заказов от мусорных вставок
3. **Authentication → Users → Add user** — создай себе логин/пароль для
   входа в `admin.html` (это не имеет отношения к клиентам сайта — это
   только твой личный вход в панель управления)
4. **Project Settings → API** — скопируй **Project URL** и **anon public
   key**
5. Вставь их в `js/api.js`:
   ```js
   const SUPABASE_URL = 'https://ТВОЙ-ПРОЕКТ.supabase.co';
   const SUPABASE_ANON_KEY = 'ТВОЙ-ANON-KEY';
   const USE_SUPABASE = true;
   ```
6. В `index.html` и `admin.html` подключение `supabase-js` уже есть (CDN),
   ничего дополнительно делать не нужно
7. В `admin.html` нажми **"⬆️ Загрузить меню из data.js"** — это разово
   перенесёт меню из `data.js` в базу для выбранного филиала

## Ключевые настройки (`js/config.js`)

| Константа | Что делает |
|---|---|
| `CONTAINER_PRICE` | Цена одноразового контейнера за каждое блюдо |
| `BRANCHES` | Список точек (`['27-71', '28-63']`) |
| `BRANCH_PHONES` | Номер WhatsApp для каждой точки — заказ летит именно туда |
| `BRANCH_MENU_LINKS` | Ссылки на графическое меню с фото (Canva) по точкам |
| `TRENDING_KEYWORDS` | Слова в названии блюда → попадает в блок "🔥 В тренде" |
| `DELIVERY_COST` | Стоимость доставки + порог, при котором она дешевле |
| `UPSELL_RANGE` | Диапазон суммы, при котором показывается подсказка про скидку на доставку |

В `js/api.js` есть ещё один важный флаг:

```js
const SHARE_MENU_ACROSS_BRANCHES = true; // все точки видят одно и то же меню
```
Когда меню начнёт реально отличаться по точкам — поставь `false`, и каждая
точка станет хранить своё меню отдельно (структура для этого уже готова).

## Особенности, которые могут быть не очевидны

- **Заморозка блюд** (кнопка ❄️ в админке) — блюдо не удаляется, а просто
  скрывается с сайта с пометкой "Временно недоступно". Название/цена/
  описание сохраняются — не нужно набирать всё заново, когда блюдо
  вернётся в наличие.
- **Смена филиала на сайте очищает корзину** — если клиент уже набрал
  корзину на одной точке, а потом переключился на другую (у которой может
  быть другое меню), корзина сбрасывается, чтобы оператор не путался.
- **Версионирование файлов против кэша браузера** — все `<script>`/`<link>`
  подключены с `?v=N`. **При каждом обновлении JS/CSS-файлов обязательно
  поднимай эту цифру** (например `v=5` → `v=6`) во всех тегах в
  `index.html` и `admin.html` разом — иначе браузеры клиентов будут
  показывать старую закэшированную версию кода, даже если файлы на
  хостинге уже новые.
- **Категории с нестандартной структурой** (Лимонады/Кофе — объём+вкус;
  Холодные напитки — свой набор размеров у каждого товара) в админке
  редактируются как JSON, а не через обычную форму — это осознанное
  решение, чтобы не плодить отдельный интерфейс под каждый частный случай.

## Локальная разработка без Supabase

Поставь `USE_SUPABASE = false` в `js/api.js` — все данные будут браться из
`data.js` и `localStorage` браузера. Полезно для быстрой проверки
интерфейса без реальной базы, но **не подходит для продакшена** — правки
в этом режиме видны только в том браузере, где их сделали.

## О безопасности

- Запись в меню (добавление/удаление/редактирование блюд) разрешена
  только авторизованным пользователям — обычный посетитель сайта не может
  ничего испортить, даже зная технические детали проекта.
- `anon key` в коде страницы — это нормально и предусмотрено самим
  Supabase, прятать его не нужно и бессмысленно (он всё равно должен быть
  виден браузеру, чтобы делать запросы). Настоящая защита — это правильно
  настроенный RLS (см. `rls_secure.sql`), а не сокрытие ключа.
- Таблица заказов открыта на запись без входа в систему (это нормально —
  клиент оформляет заказ без логина), но защищена базовой проверкой
  структуры данных (`rls_orders_hardening.sql`) от откровенно мусорных
  вставок.
